# WEB-01 — Architecture

## Components

```
                    ┌──────────────────────────────────────────┐
  player ──HTTP──▶  │ GZ::CTF reverse proxy / published port   │
                    └────────────────────┬─────────────────────┘
                                         │ :3000
                    ┌────────────────────▼─────────────────────┐
                    │ container (node, uid 1000)               │
                    │                                          │
                    │  entrypoint.sh                           │
                    │    ├─ require GZCTF_FLAG                 │
                    │    ├─ node src/generate-backup.js        │
                    │    │    └─ /app/runtime/backups/*.zip    │
                    │    └─ unset GZCTF_FLAG; exec server.js   │
                    │                                          │
                    │  server.js (Express 5)                    │
                    │    ├─ GET /                → public/      │
                    │    ├─ GET /robots.txt      → public/      │
                    │    ├─ GET /healthz         → JSON         │
                    │    ├─ GET /backups/        → dir listing  │
                    │    └─ GET /backups/:file   → zip download │
                    └──────────────────────────────────────────┘
```

* **`public/`** is baked into the image at build time and contains no secrets.
  It holds the corporate site, the CSS, the favicon and `robots.txt`.
* **`/app/runtime/backups/`** is created at build time, owned by `node`, and is
  populated **only at container start**. It is never part of the image.
* **`src/generate-backup.js`** produces the archive. It runs before the web
  server and exits the container on any failure.
* **`src/server.js`** is the only long-lived process (PID 1 after `exec`).

## Startup sequence

1. Docker starts `/app/entrypoint.sh` as user `node`.
2. The entrypoint refuses to start when `GZCTF_FLAG` is unset or empty.
3. `generate-backup.js` validates the flag (non-empty, no CR/LF/NUL) and builds
   `northstar-site-backup.zip` in a staging file, then renames it into place.
   A crash therefore never leaves a half-written archive in the listing.
4. `GZCTF_FLAG` is unset in the shell environment before `exec`, so the Node
   server process never receives the flag (verified against `/proc/1/environ`).
5. `server.js` binds `0.0.0.0:${PORT}` (default `3000`).

`HEALTHCHECK` polls `/healthz`, which does not touch the archive.

## Archive contents

| Entry | Source |
|---|---|
| `config/production.env` | generated at runtime, contains `CTF_FLAG=<GZCTF_FLAG>` |
| `package.json`, `src/server.js`, `public/*` | copied from the image |

The ZIP is generated with `yazl` (one transitive dependency, `buffer-crc32`)
rather than shelling out to `zip`, so no extra package is required in Alpine
and the flag never passes through a command line or temporary plaintext file.
All entries use a fixed mtime (`2025-10-18T02:14:00Z`) so the only variable
content between two teams is the flag itself.

## Flag lifecycle

```
GZ::CTF flag template: AXUM{forgotten_backup_[TEAM_HASH]}
        │  per-team value generated by the platform
        ▼
container env GZCTF_FLAG=AXUM{forgotten_backup_<12 hex>}
        │
        ▼
generate-backup.js → config/production.env inside the archive
        │
        ▼
entrypoint unsets GZCTF_FLAG → server process never holds it
        │
        ▼
GZ::CTF validates submissions against its own copy of the generated flag
```

The platform is the source of truth for validation; the container only receives
a value. There is no callback, database or shared secret between the two.

## Security boundaries

* Only the backup archive discloses the flag. The homepage, CSS, JS, favicon,
  `robots.txt`, 404 page and `/healthz` are free of it (verified).
* The image contains no flag and no pre-built archive; `docker run` with a
  missing flag fails closed.
* The backup directory lives outside `public/`, and only `/backups/` exposes
  it. The download handler accepts `^[A-Za-z0-9._-]+$`, rejects dotfiles, and
  verifies the resolved path stays inside the backup directory.
* The process runs as UID 1000, needs no capabilities, no host mounts and no
  Docker socket.
* `x-powered-by` is disabled; no request logging is enabled, so the archive
  request never lands in logs.
* `EXPOSE` is intentionally absent (see [DEPLOYMENT.md](DEPLOYMENT.md)).

## Design decisions

* **Express 5 + `yazl` only.** No template engine, no database, no session
  layer; the attack surface is one static site and one download endpoint.
* **Runtime archive instead of build-time archive.** A build-time archive would
  bake one flag into the image and give every team the same flag.
* **Directory listing endpoint instead of `express.static` on the backup dir.**
  `express.static` does not list directories, and enabling SPAs or a directory
  index middleware would add a dependency. The listing is ~40 lines and looks
  like a default server index, which supports the "forgotten operations
  directory" story.
* **Fixed archive name.** Players must find the file through the listing;
  robots.txt only reveals the directory, not the filename.

## Known limitations

* The archive is rebuilt on every start, so flags rotate if the platform
  recreates a container with a new flag. This is the intended behaviour for
  `DynamicContainer` and matches GZ::CTF's model.
* The container entry reported by the platform depends on
  `ContainerProvider.PublicEntry`. If it is not configured, GZ::CTF reports the
  container network address together with the published port; the port is still
  reachable on the platform host. This was observed and worked around in
  `tests/gzctf_e2e.py`, and is documented in [DEPLOYMENT.md](DEPLOYMENT.md).
